## 1. Purpose

Version `1.0.1` consumes the authenticated Registry access boundary established by:

```text
docs/REGISTRY_ACCESS_V1.md
docs/REGISTRY_CONTRACT_V2.md
policy/registry-policy.json
```

The version goal is to make the approved GitHub-authenticated Registry access model consumable by the SCTool SDK/CLI and to replace the transitional flat artifact URL metadata with a stable structured delivery descriptor, without taking ownership of Simple Connection desktop UI, installer UX, product release-session planning, or repository lifecycle classification.

## 2. Version branch rule

All Registry sessions belonging to this distribution contract version remain on:

```text
dev/1.0.1
```

Session completion does not cause a merge to `main`. The branch is merged only after every approved `1.0.1` session and the version-level acceptance gate are complete.

The implementation repository may use a matching technical branch when Registry-owned work must change code stored outside this repository. Such a branch does not transfer session authority to that repository.

## 3. Documentation layout

```text
docs/ver1.0.1/
├─ 1.0.1_Improvement_plan.md
└─ session_document/
   └─ ver.1.0.1_P{N}_{topic}.yaml
```

Rules:

1. This file owns version purpose, `current_session`, session index, acceptance, and merge state.
2. Detailed scope, exclusions, implementation evidence, validation, completion criteria, and next action live in the session YAML.
3. Session YAML files are created only when that session is approved to begin.
4. Primary session IDs are `P1`, `P2`, ...; sub-sessions use `P1.1`, `P1.2`, ... only when required.
5. Registry session authority remains in this repository even when an implementation artifact is stored in another repository.
6. A session blocked only by an external repository validation obligation does not block an independent Registry-owned later session; it does remain a version merge blocker until closed.

## 4. Responsibility boundary

### In scope

- consuming `REGISTRY_ACCESS_V1` in the SCTool SDK boundary;
- GitHub CLI credential-store identity handling;
- canonical GitHub identity resolution;
- inherited `GH_TOKEN` / `GITHUB_TOKEN` isolation;
- private Registry artifact repository authorization probing;
- fail-closed access-state handling;
- Registry package descriptor and artifact-delivery metadata contracts;
- backend-neutral artifact identity/integrity metadata;
- authenticated GitHub Release asset locator schema and validation;
- SDK/CLI machine-readable contracts and security tests;
- cross-repository implementation evidence required to prove the Registry contract is consumable.

### Out of scope

- Simple Connection renderer/UI design;
- Simple Connection installer UX or product release-session planning;
- Simple Connection PTSIP lifecycle classification or profile migration;
- production Root trust activation or `trust/trust.json` issuance;
- per-device entitlement, commercial licensing, or application attestation;
- exposing, persisting, or extracting GitHub tokens;
- artifact binary download implementation in P1/P2;
- package/channel resolution behavior changes in P1/P2;
- activating additional artifact delivery backends in `1.0.1`.

## 7. P2 descriptor direction

P2 is the formal current session for Registry Distribution `1.0.1`.

The current package schema couples exact artifact bytes to a flat HTTPS locator. P2 separates these concerns:

```text
artifact identity
+ target
+ content/integrity
+ publisher evidence
        |
        +-- stable across storage backends

delivery.type
+ delivery.access
+ delivery.locator
        |
        +-- backend-specific retrieval metadata
```

The P2 design deliberately avoids a generic bag of optional backend fields. Instead it uses a stable common envelope and a discriminated delivery union. In `1.0.1`, only:

```text
github-release-asset
```

is accepted. Future backends require an explicit later contract/schema revision.

For the current GitHub backend, the optimized locator stores only retrieval identity that cannot be derived safely from the common artifact fields:

```text
repository
assetId
```

`content.filename` is the authoritative asset name. The canonical release tag is derived from `(packageId, version)` as `sctool/{packageId}/v{version}`. Neither value is duplicated inside the locator.
