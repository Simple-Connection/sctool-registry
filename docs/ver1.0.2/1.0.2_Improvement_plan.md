## 1. Purpose

Distribution `1.0.2` establishes the Registry-owned SDK boundary that Simple Connection uses to consume Registry metadata, authenticated artifact access, delivery resolution, integrity verification, and update candidates.

This version explicitly separates two SDK responsibilities that must not be merged accidentally:

```text
Kinirin/Simple-Connection/program-sdk/sctool-sdk
= SCTool Authoring SDK
= coding-agent/developer support for designing, validating, building, testing,
  and packaging a developer's own tool as .sctool

Simple-Connection/sctool-registry Registry Client SDK
= Simple Connection integration SDK
= Registry metadata/access/delivery client behavior used by Simple Connection
  to discover, resolve, retrieve, and verify published SCTool packages
```

The two SDKs have different users, release ownership, compatibility obligations, and runtime roles. Distribution `1.0.2` therefore adopts the **two-SDK model** rather than moving all SCTool authoring responsibilities into the Registry repository.

## 2. 1.0.1 ownership correction

Registry Distribution `1.0.1` placed the `REGISTRY_ACCESS_V1` implementation physically under:

```text
Kinirin/Simple-Connection/program-sdk/sctool-sdk
```

That implementation remains valid historical evidence for the access contract, but its physical ownership is not the desired long-term SDK boundary after the responsibility clarification made during `1.0.2`.

`1.0.2` treats the following as an ownership migration target:

```text
registry-access types/state machine
GitHub CLI registry-access adapter
registry-access regression tests
```

They are to move to the Registry Client SDK. The Simple Connection SCTool Authoring SDK must return to authoring/package-production responsibility only.

Historical `1.0.1` session evidence is preserved and is not rewritten.

## 4. Repository responsibility split

### Registry repository owns

- Registry Client SDK source and compatibility boundary;
- Registry access state model and GitHub CLI access adapter;
- Registry package descriptor parsing and channel/version/target resolution;
- delivery discriminator and exact artifact locator resolution;
- authenticated artifact retrieval contract implementation;
- content filename/size/SHA-256 verification;
- client-facing normalized update candidate/result types;
- tests proving Registry contract conformance.

### Simple Connection repository owns

- SCTool Authoring SDK for third-party/developer tool creation;
- Desktop integration of the Registry Client SDK;
- local install state, activation, rollback, runtime reconcile and UI;
- its own PTSIP/profile and product path policy.

### Forbidden ownership mixing

- Registry Client SDK must not become an SCTool build/scaffold/package authoring SDK.
- Simple Connection Authoring SDK must not remain the long-term owner of Registry access/download/update client behavior.
- Registry does not directly edit Simple Connection PTSIP lifecycle declarations.

## 5. Registry SDK path issue

The current Registry repository defines root `packages/` as the canonical descriptor namespace:

```text
packages/{packageId}.json
```

Therefore adding SDK source below `packages/` requires an explicit repository-layout clarification rather than silently treating all `packages/**` as the same kind of content.

The recommended two-SDK path is:

```text
packages/registry-client-sdk/
```

This name deliberately avoids a second ambiguous `sctool-sdk` identity.

If approved, `packages/README.md`, `ptsip.yaml`, and repository governance must be changed in the **same architecture change** so that:

```text
packages/{packageId}.json
= accepted Registry package descriptor

packages/registry-client-sdk/**
= Registry Client SDK implementation
```

The validator continues to validate package descriptors through paths referenced by `registry.json`; the SDK directory is not a package descriptor.

## 7. Version-level target

The end-to-end target remains:

```text
signed/public Registry metadata
-> Registry Client SDK
-> package/channel/version/target resolution
-> registry-access-v1 authorization
-> exact GitHub Release asset resolution
-> artifact retrieval
-> filename/size/SHA-256 verification
-> verified update candidate
-> Simple Connection local install/activation/runtime reconcile
```

The SCTool Authoring SDK is not part of this consumer runtime chain.
